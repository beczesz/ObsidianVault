1. Miért van parkolva?

A Shared Basket koncepciólag ígéretes (8/10), de korai fázisban a kockázatok meghaladják az előnyöket. A döntés: v0.5+, csak stabil user base után.

⏸ PARKOLVA — v0.5+ (Sprint 5)
Forrás: v0.4-shared-basket-spec.md — Becze Szabolcs + ChatGPT döntés, 2026-04-04
# Kockázat Részletek Súly
1 Initiator burden (LEGFONTOSABB) A Host koordinál, átvesz, de nincs extra jutalom → nem lesz ismételt viselkedés 🔴
2 Időbeli koordináció Mikor zár a kosár? Ki mikor ad hozzá? Könnyen szétesik a folyamat 🟠
3 Social dependency Egyik user késik → mindenki vár; kilép → borul a rendszer 🟠
4 Mentális overhead "Mini projekt" érzés → csökkenti a repeat-et 🟠
5 Operációs komplexitás Több user, külön csomagolás, 1 cím, több fizetés → hibalehetőség nő 🟡

Kulcs insight (spec szó szerint): "Nem az a kérdés, hogy működik-e egyszer, hanem hogy ismételhető viselkedéssé válik-e."

Ha a Host egyszer megszervezi és pozitív élménye van → megismétli. Ha bonyolult volt → soha többé.

6. Mikor vegyük elő újra?

Konkrét feltételek, amelyek teljesülése esetén a DH-149 aktiválható a Sprint 5-ben.

⏸ Jelenlegi állapot: PARKOLVA
A pilot indulása után, a feltételek teljesülése esetén kerülhet Sprint 5-be
  • ⬜
    ≥50 aktív user
    Stabil user base szükséges ahhoz, hogy legyen kinek ajánlani
  • ⬜
    2nd Order Rate ≥30% stabilan (2 héten át)
    Bizonyított repeat behavior — a solo reorder már működik
  • ⬜
    Savings Engine live (v0.3 deployed)
    A shared savings logika csak a Counter-rel együtt értelmes
  • ⬜
    Nincs operációs bottleneck
    Solo rendelések fulfillment-je stabil, van kapacitás a komplexebb csomagolásra
  • ⬜
    Delivery Cluster feasibility check
    Megvizsgálandó: van-e elég sűrűség Újvárhelyen a Cluster módhoz?
Döntési fa: Ha minden feltétel ✅ → Delivery Cluster irány (egyszerűbb) vs. Full Shared Basket (komplexebb).
Ha a Cluster nem feasible (nem elég sűrű a rendelési mintázat) → Full Shared Basket tervezési fázis indul.
